### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** Resolve the forge once for the program, per **Forge** in `playbooks/opening-a-pr.md`. One native agent per PR owns its change end to end: build, first push, a draft PR opened before self-proof, self-proof (gates, CI, receipts), skeptical triage of any review-bot comments (Bugbot or equivalent) per `../references/bugbot-triage.md`, a slop-strip (the **deslop** skill), `no-comments` (the **no-comments** skill), and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR as a draft. Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on the wake chain.** Run the root's audit tick per Autopilot-full step 6, from "Run an audit tick" to the end of the step, with `skills/cstack-mode/playbooks/autopilot-stack.md` as the recorded playbook path.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, record the program objective and completion predicate in the durable plan. Use the active task and an available authorized native continuation mechanism for work beyond it. Report unsupported persistence before starting dependent work. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of loop-green. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified. The root marks it ready per **Readiness** in `playbooks/opening-a-pr.md` once CI is green on the appended head and its verdict still holds under the patch-id rule. For a stack child, merge-ready means it merges cleanly once its parent lands.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, with `--onto` per **Size and stacks** in `opening-a-pr.md` when the parent was rewritten, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it as a draft with `gh pr create --draft --base <parent-branch>`, or the Origin equivalent, according to the resolved forge. Retarget an existing PR with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in the resolved forge, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.

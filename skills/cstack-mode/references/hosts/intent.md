# Intent host note

Apply [the runtime contract](../runtime.md) first. This note maps its capabilities to Intent, a workspace app whose daemon, `intentd`, runs Claude Code, Codex, and other agent CLIs as providers. You are in Intent when your tools include `workspace_api` and your system prompt lists `<available_skills>`. Claude Code's own tools can still appear there, so follow this note rather than the Claude Code note.

Checked at: intentd 0.10.33

That line names the release in the form `intentd --version` prints. Each claim below about Intent carries a label that says how far it was checked at that release.

- "Read from source" links `intentd`'s source at the `v0.10.33` tag.
- "Read from docs" links Intent's official docs, which are not pinned to a daemon release.
- "Observed" was seen on a 0.10.33 daemon by the agent that wrote the claim.
- "Relayed" was reported by another agent on a 0.10.33 daemon and was not rerun for this note.
- "Plugin workflow" names the route an agent follows in Intent, rather than a limit enforced by the daemon.

The capability routes with no label come from the `workspace_api` tool's own description. The **Install** paragraph describes `hooks/intent-install.sh` in this plugin. In **Headless runs**, the Linux socket path and the proxy fallback were not rerun at this release. A newer daemon can differ, so recheck a "cannot" or "has no" claim before you design around it, and rerun a relayed claim before you depend on it.

The plugin reaches an Intent agent by two routes. Intent's own skill catalog is the first, and the install command fills it. Specialist configuration belongs to setup. The provider is the second. Intent no longer isolates its providers. Release 0.10.25 reverted the daemon-owned provider configuration ([intentd PR 2331](https://github.com/intent-hq/intentd/pull/2331)), so a provider loads its own plugins and hooks inside Intent. A person who also installed the plugin in Claude Code or Codex gets that copy and its session-start hook in every Intent agent on that provider. This was observed on a Claude Code agent and relayed for a Codex agent.

Delegation limits. Depth counts from the agent the person started, which is depth 0, and `ws.agent.status` on your own id shows yours as `metadata.delegationDepth`. An agent at depth 2 cannot delegate ([the delegate guard, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10561-L10577)). A depth-2 agent quoted the same error (relayed). The call fails with this text:

```text
Cannot delegate task: maximum delegation depth (2) reached. You are at depth 2. Please complete this task directly instead of delegating further.
```

`ws.agent.delegate` accepts `behaviorPrompt`, and no code in the delegate service reads it (read from source). The [binding](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/bindings/agent.rs#L738) parses the field, and the service does not pass it to the new agent. One Claude Code child and one Codex child, each delegated with a specialist and a behavior prompt, saw the specialist's own prompt and not the behavior prompt (relayed, one run each, self-reported).

Skill directories. `<project-skills>` is `.agents/skills` in the project, which Intent and Codex outside Intent both read. `<user-skills>` is `~/.intent/skills`. Intent scans eight roots ([skill discovery, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/skills.rs#L191-L253)). When two roots hold a skill of the same name, Intent lists the one from the higher root in this order:

1. `.intent/skills` in the project
2. `.augment/skills` in the project
3. `.claude/skills` in the project
4. `.agents/skills` in the project
5. `~/.intent/skills`
6. `~/.augment/skills`
7. `~/.claude/skills`, or `skills` under `CLAUDE_CONFIG_DIR` when that is set
8. `~/.agents/skills`

Intent does not scan `.codex/skills`, in the project or in the home directory. Intent names a skill from its frontmatter `name` and lists any `SKILL.md` in a root whose frontmatter has a `name` and a `description`, a `principle-*` skill included ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/skills.rs#L680-L746)).

Instructions file. Intent adds one project file to every agent's system prompt. It is the first of `CLAUDE.md`, `AGENTS.md`, `.intent/guidelines.md`, and `.augment/guidelines.md` that exists. When none exists, Intent adds every `.intent/rules/*.md` and `.augment/rules/*.md` instead ([rules, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/rules.rs#L83-L200)). It does not follow `@` imports. The provider can also load its own instructions file, as Claude Code does with `CLAUDE.md` and its imports. In a project with a `CLAUDE.md`, put the mode line in `CLAUDE.md` itself, above any import of `AGENTS.md`.

User instructions file. None. Intent keeps a person's rules in its settings store, under Settings, Agent Behavior ([settings](https://intentapp.dev/docs#settings-configuration)), so give the person the rule text to paste there.

## Seats

Intent starts a seat with its listed id below as `specialist` and the workflow's brief in `agentInstructions`. Check `ws.agent.listSpecialists()` first. An absent id means setup has not run for that seat. Omit `specialist` and use `agentInstructions` under [Seat delivery](../runtime.md#seat-delivery), avoiding the unknown-id error [read from source at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10660-L10664).

| Seat | Specialist id | Seat file in the plugin |
| --- | --- | --- |
| lead | `<plugin>-lead` | `agents/lead.md` |
| builder | `<plugin>-agent` | `agents/<plugin>-agent.md` |
| worker | `<plugin>-worker` | `agents/worker.md` |
| investigator | `<plugin>-investigator` | `agents/investigator.md` |
| reviewer | `<plugin>-reviewer` | `agents/reviewer.md` |
| verifier | `<plugin>-verifier` | `agents/verifier.md` |
| advisor | `<plugin>-advisor` | `agents/advisor.md` |
| scout | `<plugin>-scout` | `agents/scout.md` |

The lead is the agent a person starts, rather than a delegation target. Setup configures every specialist's explicit provider, model, and effort through **Seat setup** below. No seat definition in the plugin carries those settings. A single seated call passes no model fields and uses the configured specialist instead of a `Models:` block. This resolution is [read from source at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10666-L10723).

For a reviewer panel, the delegating agent reads the specialist's `modelOptions` menu and passes entry k's `provider`, `model`, and `reasoningEffort` together for call k. Apply the same route to verifier lanes. For a lane past the menu, pass Intent's default provider, model, and effort explicitly, so the specialist's default does not refill the lane. Read settings with `intentd settings <name>` (observed from its help at 0.10.33). Resolve `model.defaultProvider`, then that provider's entry in `model.providerDefaults`, then `model.default`, as [read from source at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L424-L466). Use `model.defaultReasoningEffort`, or pass an empty `reasoningEffort` to clear an unset default, as [read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L872-L913). Report a missing provider or model as a missing lane. The resolution of explicit values ahead of specialist values is [read from source at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10666-L10723). Report each lane's resolved family and call the panel diverse only when the families differ. A reviewer never delegates.

Model roles for calls that have not migrated. A `native` role passes `provider`, `model`, and `reasoningEffort` to `ws.agent.delegate`. Pass `provider` with every `model`. A call that passes a model without its provider drops the specialist's provider, and Intent uses its default provider ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10666-L10682), and relayed). Those calls keep their existing `Models:` route until they migrate. A delegate with no `specialist` gets no specialist prompt and runs on Intent's default provider, model, and effort settings (relayed from one `ws.agent.status` read). The missing prompt is [read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/lib.rs#L2359-L2400).

Specialist files. A specialist is a Markdown file whose body is the prompt. Intent reads these frontmatter keys ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L402-L446), with the other keys defined in the same file): `name`, `description`, `codingAgent`, `model`, `reasoningEffort`, `roleReminder`, `agentType`, `role`, `icon`, `hidden`, `modelOptions`, `teamAgents`, and `aliases`. No key names skills or permissions.

- Tiers. Intent folds its built-ins, then `~/.intent/specialists`, then `.intent/specialists` in the workspace's own root, and the last file with an id wins ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1286-L1296)). A project file is listed by `ws.agent.listSpecialists` (relayed). Intent reads it from the workspace's root, and a copy in an agent's sandbox was not listed (relayed).
- A same-id file replaces a built-in's whole prompt, name, and description ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L901-L921)). A `verifier.md` that held only `reasoningEffort` left that specialist with an empty prompt (relayed). The keys `codingAgent`, `model`, `reasoningEffort`, `agentType`, `role`, `icon`, and `modelOptions` inherit from the lower tier when the file omits them.
- Tool limits. Intent limits tools in two places, and what a key removes depends on the place and on the provider. Neither key makes a read-only sandbox.
  - Workspace tools, on every provider. `agentType` values `commit-message`, `pr-description`, `code-review`, and `code-walkthrough` remove the `workspace_api` tool itself. No other `agentType` value and no `role` removes a workspace tool ([the denylist](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/tool_restrictions.rs#L152-L185), applied by [the workspace tool server](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server.rs#L144-L159), both read from source).
  - The provider's own tools, such as its shell and file editor. What `role` and `agentType` remove differs by provider ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/tool_restrictions.rs#L270-L304)). On Claude Code, `role: orchestrator` removes `Edit`, `Write`, and `NotebookEdit` and leaves the shell ([session options, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_session.rs#L1838-L1866)). For any other provider, read the linked code before you rely on a removal.
- `modelOptions` is an advisory menu, written as a JSON array on one line. Intent includes non-hidden specialists' menus in an agent's `ws.agent.delegate` tool description ([read from source at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/lib.rs#L2222-L2279)). For a hidden seat, read its menu from `ws.agent.listSpecialists()` instead. The menu does not restrict calls, so apply an entry by passing its provider, model, and effort. When a call passes no effort, the first entry that matches the resolved provider and model supplies the effort, ahead of the file's own `reasoningEffort` ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1143-L1161), and relayed).
- Edits. Intent's `specialist.edit` call writes the file at the specialist's path, and for an installed link that write lands in the plugin's own file ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1934-L1970)). Whether the desktop app's specialist editor uses that call was not checked, so treat an edit there as a change to the plugin's file.

Plugin root. Take it from a skill's resource directory, which the system prompt lists as `resource_directory` and `skill.list` returns as `resourceDirectory`. For a linked skill that is the skill's real directory, and the plugin root is two levels above it. The skill's `location` is the installed link under `~/.intent/skills`, and the path above that link does not hold the plugin.

Install. The person runs `npx -y github:<owner>/<repo>` with the plugin's repository. The entry point, `hooks/intent-install.sh`, runs the multi-host command in `hooks/install.mjs`. Installed hosts are selected by default. `--yes` updates only installed hosts without a question, and a run without a terminal does the same. `--hosts intent` selects Intent explicitly. `--report-only` reads detection data and prints planned commands without delivering anything.

For Intent, the command delivers the GitHub package fetched by npx. It reads the Git source from the package manager's adjacent `package-lock.json`; `--source <owner>/<repo>` overrides it. When the requested source differs from the running package, it asks npx to fetch that source and run its Intent delivery. It never uses a local checkout as the source. Without either source, it reports the npx command to run and continues the provider updates.

`hooks/intent-deliver.sh` keeps the delivered package under `${XDG_DATA_HOME:-~/.local/share}/<plugin>` and links every visible skill into `~/.intent/skills`. It creates no specialist links. Its record beside the copy stores every host entry it owns. On an older install, it removes a persona link only when the current link matches that record. It leaves a personal regular file at the same path unchanged, including a file setup wrote. A personal file prints `left your own <name> as it is` in the final table and is a successful result. Missing or unreadable records authorize no removal. Keep the copy safeguards and the two-case directory deletion rule in `hooks/intent-deliver.mjs`.

Persistent mode. Two things can turn the mode on in Intent. The first is the provider's own copy of the plugin. Its session-start hook runs inside Intent, so `hooks/mode.sh` and `CSTACK_MODE` take effect for an agent on that provider. The hook's text was observed in a Claude Code agent and relayed for a Codex agent, and `CSTACK_MODE` was observed in a Claude Code agent's shell. The second is an instruction. The project's instructions file covers one repository. For every project, the installer adds a personal rule on any run that finds no `<plugin>-mode` entry in `~/.intent/skills`, which is normally the first run. Deleting that link and rerunning adds the rule again, unless the person's rule text still names the mode. An entry of that name that is not the plugin's stops the rule being added. The installer adds the rule through `intentd call rules.update` with `workspaceId` `global` and `ruleType` `workspace`:

```markdown
Before any other step, read the `<plugin>-mode` skill's SKILL.md from your skills list and follow it for the rest of the session, unless a plugin seat file in your instructions says "Set the plugin's mode aside for this task". In that case, your brief is the whole task.
```

Intent stores the rule as the first paragraph of the person's own rule text, with nothing that marks it as the plugin's. It reaches ordinary workspace agents and their delegates, and not the Assistant workspace ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/rules.rs#L471-L500)). A thin seat is exempt when its own file arrives as a registered specialist's body or as the whole file in the brief, per [Seat delivery](../runtime.md#seat-delivery). The lead and builder read the mode. The provider hook uses the same seat-file exemption as the rule. On each install or update, the installer compares only the first paragraph with its list of exact earlier rule texts, ignoring trailing whitespace. It replaces a match with the new rule, preserves that whitespace, the remaining text, and the enabled state, and reports the change in the final table. Any other edit, a moved rule, or a removed rule stays unchanged. The table says that new rule text is available and prints the text to paste under Settings, Agent Behavior. If the first paragraph already equals the new rule, the installer leaves it unchanged without a paste prompt.

When it can't reach `intentd`, the installer prints the rule for the person to paste. On a first install it also prints the rule when the person's rule is switched off and not empty. A first install writes a switched-off, empty rule and switches it on. The provider hook and the personal rule are separate switches. `hooks/mode.sh off` and unsetting `CSTACK_MODE` stop only the hook. The rule still tells workspace agents to load the mode unless their seat file sets it aside. The person turns the rule off by removing that paragraph.

Sandboxes and attribution. A delegate gets its own sandbox only under two conditions ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10782-L10848)). The first is that isolation is on, through `isolation: "cow"` on the delegate call or the `workspace.cowIsolation` setting, which is off by default. The second is that the workspace is a direct-mode, copy-on-write, or direct-checkout workspace. A worktree-mode workspace keeps one checkout that the delegate shares with its parent. Before you rely on isolation, check your working directory. A sandboxed agent works in a checkout under the workspace's `sandboxes/<agent id>/` directory, on a branch named `sb/<agent id>` (observed in one workspace with `workspace.cowIsolation` on).

After a successful merge-back, Intent calls `discard_sandbox` to remove the sandbox directory, including its local branch ([caller](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/lib.rs#L9931-L9972) and [removal](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/sandbox_ops.rs#L312-L334), read from source). That removal happened when a delegate's turn ended (relayed, one run on 2026-10-10). A git worktree made from a delegate's sandbox stopped working when that delegate's turn ended, because the worktree's git data lives in the sandbox (observed, one run).

A delegate committed in its sandbox before its turn ended, and Intent carried each commit onto the workspace's branch with its author, committer, and message intact (relayed, two runs on 2026-10-10). The [sandbox merge code](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/sandbox_ops.rs#L665-L674) keeps those original values (read from source).

Two paths commit a delegate's work without the agent.

- Intent's `git.autoCommit` setting is on by default. When a task-linked agent goes idle, Intent commits its changes with a generated message and `Agent-Id:` and `Linked-Note-Id:` trailers, outside the **Authorship** rule in `playbooks/opening-a-pr.md`. Pass `skipAutoCommit: true` to `ws.agent.delegate`, which skips this commit ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/auto_commit.rs#L262-L277)), and give the person the setting to turn off: auto-commit in Intent's Git settings, or `intentd settings git.autoCommit false`.
- When Intent merges a sandbox back, it first commits its dirty state with the subject `Auto-commit dirty state for <agent id>` ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/sandbox_ops.rs#L404-L445)). The dirty check counts ordinary untracked files and excludes ignored files and untracked nested Git repositories ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/nested_repos.rs#L38-L66)). In one run that commit landed on the workspace's own branch when the delegate's turn ended, with the machine's git identity and no trailers, and `skipAutoCommit: true` did not prevent it (relayed, one run).

When Intent can resolve a git identity for the agent's checkout, it sets `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, and `GIT_COMMITTER_EMAIL` in the provider's process, and it keeps a value that is already set ([the resolver](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-git/src/identity.rs#L44-L77) and [its caller](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_manager.rs#L12601-L12605), read from source, and the four names observed in an agent's shell). Git ranks these variables above `-c user.email` and above the repository's own config. A commit made with only `-c user.email` kept the inherited address (relayed, one run). When the person approves another identity for a commit, set all four variables on that commit command, then confirm the author and the committer with `git log --format=fuller` before you push.

Commit and PR route (plugin workflow). In Intent this route replaces the **Worktree** paragraph in `playbooks/opening-a-pr.md`. Build in Intent's checkout, with no added worktree or separate clone. Use one workspace branch and one PR for the work. A second PR, including a child in a stack, needs its own workspace. Intent's docs describe a workspace as a git branch with agents and notes, and the **Changes** tab as that branch's timeline, including its PR ([read from docs](https://intentapp.dev/docs#git-code-changes)). Follow this route:

1. Builder. Build from the workspace's own branch in the checkout Intent supplied. When isolation applies, use the sandbox described above.
2. Every agent, reviewers and verifiers included. Use `tmp/<task>/` inside the workspace, per [Scratch files](../../SKILL.md#scratch-files). Use the workspace checkout's `path` from `ws.workspace.info()` for files the lead or person reads after your turn. A sandbox is discarded after successful merge-back, so use its `tmp/<task>/` only for throwaway scratch. Keep these files inside the workspace, because Intent cannot open a file outside it for the person (relayed). The ignore fallback in that rule ignored the task folder without a tracked-file change (relayed, one run).

   Every agent that commits. Commit only files that belong to the change. Use plain `git commit` in place of Intent's standing `ws.git.commit` rule because the helper added an `Agent-Id:` trailer (observed, one run). That probe used an explicitly selected sandbox and kept the person's author and committer identity. Set `GIT_AUTHOR_NAME` and `GIT_COMMITTER_NAME` to the person's own forge name. Set `GIT_AUTHOR_EMAIL` and `GIT_COMMITTER_EMAIL` to that person's forge email, such as their forge noreply address. Put all four values inline on each commit command. Before asking, read the four inherited variables and the branch's last commit. Ask the person once when their identity is still unknown. Confirm each commit's author and committer with `git log --format=fuller`. Follow **Authorship** in [opening-a-pr](../../playbooks/opening-a-pr.md), keep trailers and attribution lines out of the commit message, and read it back in full with `git log -1 --format=%B`. A sandboxed agent commits before its turn ends and ends every turn with an empty `git status --short`.
3. Lead agent. Keep the workspace checkout clean while a builder runs. Here, clean means no uncommitted change to a tracked file. Inspect `git status --short`, `git diff`, and `git diff --cached`. An untracked `?? .intent/` entry is expected when Intent's default ignore file re-includes itself and `config.json` ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/repo_config.rs#L23-L30), and relayed). Preserve that directory and its contents. Do not commit it to clear the status. Stage only explicit files that belong to the change, and never use `git add -A` in the workspace checkout. Account for any other untracked project files before merge-back. Overlapping uncommitted changes there block merge-back ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/sandbox_ops.rs#L456-L483)). After the builder's turn ends, read the workspace branch's log in the workspace checkout. Use the `path` returned by `ws.workspace.info()`, which resolves the workspace's own checkout ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/bindings/workspace.rs#L609-L616)). Compare the carried commits' authors, committers, and full messages with the builder's report.

## Seat setup

This is the plugin workflow. Setup runs `node <plugin-root>/hooks/intent-setup.mjs` with `report`, `apply`, or `revert`. The command needs Node, which the install command also uses. Read its `--help` before preparing input.

1. Collect the provider, model, and effort choices already offered by the person's Intent. Keep the catalog and choices in the project's ignored `tmp/<task>/` folder. Use the person's current catalog, never a model list in this repository. `providers.catalog` supplies provider ids ([router, read from source at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-transport/src/router.rs#L4018-L4023)). A model row's `effortLevels` supplies its offered efforts ([parser, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/provider_models/parse.rs#L154-L194)). If the current catalog is unavailable, report that missing input and ask the person to supply Intent's choices. Do not guess an effort for a model that offers none.
2. Ask for one explicit triple per seat. The investigator is asked too. Recommend no model or effort. Explain that a seat requests more passes for more thoroughness. Ask for an ordered review menu and use it for reviewer and verifier. Every menu entry has all three fields. Its first entry repeats the seat's own triple, and no pair of provider and model appears twice.
3. Write the input JSON files under `tmp/<task>/`. The catalog shape is `{"providers":[{"id":"<provider>","models":[{"id":"<bare model>","efforts":["<effort>"]}]}]}`. Choices are keyed by the eight seat names, with `provider`, `model`, and `reasoningEffort`. Reviewer and verifier also carry `modelOptions`, an array of those triples. Values are the person's selections, never defaults.
4. Run `report --choices <file> --catalog <file>`. It locates the installed copy through the install record's matching mode link. Show every before and after value, including a personal builder file if present, and the report's `approval` digest. A report writes nothing. Ask for a yes to that exact report. On a no, run no apply.
5. After the yes, run `apply --choices <file> --catalog <file> --yes --approval <digest>`. Preserve any `--show-all` choice on both report and apply. A changed file or input invalidates the approval and needs another report and yes. Apply writes eight regular files and records each prior value before overwriting. It never follows a specialist link to write its target. An unrecorded link is kept for the person to move aside. A matching installer-record link can be replaced. Revert restores it only while the installer still records that exact link; after an installer update drops its entry, revert removes the setup file and leaves the path empty. Setup leaves the install record alone.
6. Confirm the resulting files with `specialist.list`. On a throwaway home and daemon first, test hidden delegation and a no-model delegation per seat. Check the child's resolved triple and its first seat-file read. If hidden delegation fails, show a report with `--show-all`, get a yes, and apply that report. Say why all eight now show. The helper does not launch agents or claim this live result.
7. On a revert request, run `revert --report-only` to show the undo, then `revert` within the person's authorization. Revert restores prior files and modes in reverse order. It restores a prior link only while the installer still records it. It removes newly written files only while their bytes and mode match the record. It keeps and names later edits. When an entry holds a prior regular file, revert retains its original bytes in the record until they are restored. To recover that original, move the later-edited file aside and run revert again. If the seat file was deleted, revert restores the prior file directly. A second revert changes nothing until the person clears an unresolved path. An interrupted apply is recovered before reverting earlier changes. Recovery visits only the writes that apply reached. It closes the interrupted run even when a later edit holds an original in the ready record. A filesystem error keeps the interrupted journal for a retry. A lock journals the owner PID and the exact temporary paths it attempted to create. A later write command clears a matching owner record only when signal zero proves no process has that PID. A live or unknown owner keeps the lock. The error gives an exact move-aside command to run only after the person confirms no setup run is active. An atomic acquisition file serializes lock takeover. Only its creating run removes it. An interrupted acquisition is kept with the same manual recovery instructions. The helper names and preserves earlier-run temporary files; only the creating run may clean its own temporary file. A failed filesystem restore names its paths and retains the journal for another revert. For a damaged or outdated setup record, every write is refused with its path and recovery steps. `revert --report-only` still gives a diagnostic without writing. Keep a backup of that record for manual recovery, or use the helper from its recorded release and home.

The specialist frontmatter uses `codingAgent` for provider, `model`, `reasoningEffort`, the seat's description, and `roleReminder` for its pointer. Its body is one line pointing at `agents/<seat>.md` in the installed copy, or `agents/<plugin>-agent.md` for builder. The file uses `hidden: false` for lead and `hidden: true` for the other seven. These fields are parsed at v0.10.33 ([scalars](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L402-L446), [visibility](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L821-L845), both read from source). Hidden definitions remain in [the specialist list](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1765-L1778) and [canonical id resolution](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1339-L1382), read from source. That source result does not replace the live hidden-delegation check.

The setup record is `<plugin>-setup-record.json` beside `<plugin>-install-record.json` under the absolute `XDG_DATA_HOME`, or `~/.local/share` otherwise. It holds the plugin root, version, and each file's before and after state. Regular-file state carries base64 bytes, a SHA-256 digest, and permission bits. Link state carries the target. Visibility is recorded in the specialist's bytes. This helper changes no daemon setting or rule. Apply starts an empty pending journal, adds each write immediately before attempting it, and rolls back only those entries on failure. Recovery checks the installer's current link ownership just as a normal revert does. Record writes use atomic replacement and mode `0600`. Simultaneous setup commands fail on the same lock rather than overwrite each other's record.

Discovery boundary. `host.providerDiscovery` can fill unset default provider and model settings ([read from the applying branch at v0.10.33](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-transport/src/host.rs#L469-L488)). Do not call it as a read-only setup preflight. `models.list` can persist its model cache ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/model_catalog.rs#L808-L840)). Reuse choices already exposed by Intent or supplied by the person. A fresh discovery run remains a separate approval decision; this helper neither runs it nor changes model defaults.

## Grill documents

Follow [grill-with-docs](../../../grill-with-docs/SKILL.md) for grill and align rounds, including rounds by a delegated agent.

Use the workspace's one Spec note for the spec and align draft. Put goal, status, what waits on each person, grills, and decisions first. Put the tier's template sections and evidence after them. Notes and the Spec are [documented by Intent](https://intentapp.dev/docs#context).

Create each grill through an `@@@task` block under the Spec's Grills section with `ws.note.add`. Title it `Grill: <topic>`. Read `createdTasks` and `warnings` from the result. Set the grill task to `in_progress` with `ws.task.updateNoteStatus`. Its task link shows `[/]` while open and `[x]` when complete ([status mapping, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/note_ops.rs#L434-L441)). Share the returned note link in the reply.

Read threads with `ws.comment.list(noteId, { includeComments: true, status: "open" })` and their full comments with `ws.comment.getThread`. Reply in the thread with `ws.comment.respond`. These routes are in [the comment binding, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/bindings/comment.rs). Ask people to anchor a comment on a heading or a sentence. A comment in one table cell works through the API, but a selection across cells can fail to anchor (relayed, app selection untested). A code-block comment puts literal anchor markers inside the code (relayed).

Read and handle existing comments before starting the watch. Then schedule a background hook with `ws.hook.schedule`, `delayMs: 60000`, and `perpetual: true`. Choose `ttlMs` for the expected wait plus a margin. Its code lists comments on the open grill notes, keeps the ids of comments from people in `hookState`, and wakes the agent only for an unseen one. Cancel it with `ws.hook.cancel` when the grills end. On a wake, read each reported comment and reply in its thread even when another agent has replied since it was posted.

The `delayMs` hook expires within 24 hours, and re-arming starts with no state, so read and handle existing comments again before scheduling it.

The following pattern stayed quiet through test agents' comments and woke an agent for a person's comment on 2026-10-10 (relayed observation, one 0.10.33 workspace). Replace the note id with the open grill note ids:

```js
const ids = ["<open-grill-note-id>"];
const seen = (hookState && hookState.seen) || null;
const now = {};
const fresh = [];
for (const id of ids) {
	const th = await ws.comment.list(id, { includeComments: true });
	for (const t of (th.threads || [])) for (const c of (t.comments || [])) {
		if (c.authorType !== "user") continue;
		now[c.id] = 1;
		if (seen && !seen[c.id]) fresh.push({
			noteId: id,
			commentId: c.id,
			on: String(t.targetedText || "").slice(0, 80),
			by: c.author,
			text: String(c.content || "").slice(0, 400)
		});
	}
}
if (!seen) return { dispatch: false, state: { seen: now } };
if (fresh.length) return {
	dispatch: true,
	message: "New comments from a person: " + JSON.stringify(fresh),
	state: { seen: now }
};
return { dispatch: false, state: { seen: now } };
```

The `authorType` filter excludes ordinary agent comments even if an agent replies in the same thread before the next check. It does not authenticate a person. An agent can supply any comment author, so confirm the decider from the conversation's known participants and label synthetic comments as test inputs (relayed from a probe). Agent comments and replies also publish `comment:added` as System ([event publication](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/lib.rs#L14256-L14272) and [excludeSelf filter](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/event_subscriptions.rs#L336-L340), read from source). The hook filters the comments themselves rather than those event actors.

Settle an answer in the same turn. Write it into the Spec's Decisions with its question number, owner, and date. Reply where it arrived, including each open thread on the question. Resolve those threads before removing the question's section. The comment binding has no resolve method. Get `<workspace-id>` from `ws.workspace.info()`. The probe saw the resolve logged under the machine owner's name (relayed). Use the daemon route below, which preserves the note text (relayed, and [read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/lib.rs#L27877-L27883)):


Use `ws.note.edit` and `ws.note.add` for small edits. Read `rawContent` with `ws.note.read` before a necessary full replacement, and keep every `<!--anchor:...:start-->` and `<!--anchor:...:end-->` marker.

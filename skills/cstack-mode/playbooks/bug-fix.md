### Bug fix

**You own this task. Plan, review, verify.** Stay in the lead.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Reproduce it yourself on the matching surface via the control skill (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires.
   Make the repro a **red loop**: one command you have already run that goes red on the user's exact symptom, gives the same verdict every run, and finishes in seconds. Reach for the cheapest seam that hits the bug path, in roughly this order: a failing test, an HTTP script against a dev server, a CLI run with a fixture diffed against a known-good snapshot, a headless browser script, a replayed captured payload or trace, a throwaway harness around one function, a property or fuzz loop, a `git bisect run` script between a good and a bad state, or the same input through old and new versions. For a flaky bug, raise the reproduction rate (loop it, parallelize, add stress) until it fails often enough to debug. Then shrink it, cutting inputs, callers, config, and steps one at a time, until every remaining element is load-bearing. Step 1 is done when the loop is red, tight, and minimal. Without one, report what you tried and ask for an environment, a redacted captured artifact, or permission to add instrumentation, rather than theorizing.
   Redact secrets in every command, output, and artifact you show as `<REDACTED>`. Keep credentials in environment variables the loop reads.
2. Binary-search the cause. Write three to five ranked hypotheses before you test any. Each one states its prediction ("if X is the cause, changing Y makes the loop go green"). A hypothesis with no prediction gets sharpened or dropped. Then rule them out until one survives. Seed them by invoking `how` over the affected subsystem and `why` for regression history. When a working case exists (an earlier commit, a passing sibling input, a similar code path), diff it against the failing case and seed a hypothesis from each difference. When a test fails only in the full suite, bisect the suite to find the earlier test that leaves shared state behind. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs, one variable per probe. Tag each debug log with a unique prefix such as `[debug-a4f2]` so one grep removes them all before commit. Drive a long or stubborn hunt with the host's supported continuation capability. Confirm the surviving *mechanism* with runtime evidence before step 3.
3. Plan the fix. If it adds a module, reshapes a public interface, or has more than one viable shape, invoke `architect` first. Write a small fix yourself. Delegate a large one to a subagent on the `build` role with a specific scope, and review its diff.
4. Verify on the same surface. The red loop now passes against the original, unshrunk scenario, and a grep for the debug prefix comes back empty. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence. When a test is flaky on timing, replace its sleep with polling for the awaited condition under a timeout; keep a fixed delay only when the test measures timing itself.
5. Stage the commits so the failing repro lands before the fix in git history. Put the regression test at a seam that exercises the bug as its real callers trigger it. When no such seam exists, say so in the PR as a finding, since a shallower test gives false confidence. Invoke `tdd` for the failing-test-first cadence when the bug has a cheap local test path. Skip it when the test would be expensive, integration-heavy, or unclear.
   This is the canonical **sequence-verifiable-units** principle skill, the failing test first and the fix on top.
6. Run **Opening a PR**.

**Reply:** what was broken, the hypothesis that survived, fix, how you verified. Paste failing-then-passing repro output verbatim.

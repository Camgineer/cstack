# Simple-As Writing

Use this standard for every piece of prose.

The reader should understand the point on the first pass and know what to do next.
The goal is clear transfer of meaning, not impressive language.

## Standard

- Lead with the point.
- State the desired outcome in observable terms.
- Make the next action explicit when one exists.
- Use the simplest word that keeps the meaning.
- Write one main idea per sentence. Split long sentences.
- Prefer active voice, present tense, and strong verbs.
- Use concrete facts, names, dates, owners, and criteria.
- Keep necessary technical terms. Explain them in plain language when the reader may not know them.
- Match detail to the reader's context and skill.
- Keep useful warmth, humor, rhythm, emotion, and strong opinions when they help the message.
- Use positive instructions. State the target behavior first; reserve a prohibition for a real guardrail.
- Write without em dashes.

Translate vague words into behavior, evidence, or criteria. Give special attention to terms such as professional, proactive, strategic, aligned, thoughtful, confident, polished, urgent, high quality, better, strong, engaged, supportive, efficient, and optimized.

For an action request, include the facts the reader needs: what to do, how to do it, when it matters, why it matters, and what is blocking it. Include only the parts that affect correct action.

## Editing loop

Use this sequence for drafting, rewriting, or revising. Finish each step before moving on.

1. **Set the outcome.** Decide what the reader should understand, decide, feel, or do after reading. The outcome is done when it is specific enough to observe.
2. **Fit the reader.** Identify the reader, shared context, stakes, and required detail. This is done when you know what the reader can safely infer.
3. **Write the point first.** Put the decision, result, risk, or ask at the front. This is done when the first sentence gives the reader a useful orientation.
4. **Make action visible.** Name the owner, action, timing, and evidence when they matter. This is done when the reader can act without guessing.
5. **Cut and simplify.** Remove filler, repeated ideas, jargon, abstract labels, weak openings, and detail that does not change understanding or action. This is done when every remaining sentence earns its place.
6. **Strengthen the prose.** Prefer active voice, concrete nouns, strong verbs, short sentences, and plain words. This is done when a busy reader can follow it in one pass.
7. **Read for speed and correctness.** Check the first pass, tone, facts, timing, ask, and evidence. This is done when the message is clear, accurate, and ready for its stated use.

For important or repeated work, use a visible checklist. For long work, test the shape early with an outline, a small sample, or one representative example.

## Format rules

- **Rewrite:** Return the improved version. Add explanation only when it materially helps.
- **Critique:** Name the biggest clarity problems, give the revised version, then name the most important rules used.
- **Draft:** Infer the reader, outcome, next action, and necessary context. Produce the shortest version that works.
- **Punchy:** Compress harder while keeping the point, action, and required context.
- **Professional or executive:** Lead with the decision, result, risk, or ask. Keep the language simple.
- **Chat or status:** Use normal prose. Keep a short update short. Add structure only when it makes the message easier to scan or act on.

When the user asks for rewrite or critique scoring, score 1 to 5 for simplicity, sentence clarity, concreteness, actionability, compression, and reader fit. Aim for 5 where the format allows. Do not self-score ordinary chat.

## Prose about code

Apply the full standard to PRs, tickets, technical docs, UI copy, error messages, comments, and delegation prose.

When shaping code itself, use the standard lightly:

- Choose names a stranger can read and that state the real concept, effect, units, state, ownership, or failure.
- Give each function or small unit one job.
- Keep interfaces and error contracts explicit.
- Remove empty wrappers and needless indirection.
- Keep comments for rationale, external constraints, protocol quirks, and measured tradeoffs. Do not narrate code.

Keep required domain terms and established code idioms. Clarity does not mean baby-talk, comment spam, or replacing precise terms with vague ones.

## Final check

Before sending, ask:

- Is the main point obvious?
- Is the desired outcome clear?
- Is the next action clear?
- Are the words simple and the sentences easy to scan?
- Is the language concrete, active, and specific?
- Did I replace vague labels with behavior, evidence, or criteria?
- Did I include timing and evidence where they matter?
- Did I match the detail to the reader?
- Can the reader understand it correctly on the first pass?

If removing a word or sentence loses no meaning, evidence, needed emotion, or context, remove it.

Simple writing takes more thinking, not less. Make the meaning obvious. Make the action obvious. Then stop.

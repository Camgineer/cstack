### Opening a PR

Invoked at the end of every other playbook.

**Worktree.** Fetch the trunk, then work from a git worktree off the fetched trunk tip, not the local ref. Subagents inherit it. Name its base SHA in each subagent's brief. A subagent's claim that something is absent holds only for that SHA, so recheck it against the current trunk before you act on it. Multiple native subagent calls on the same branch each get their own worktree, or `git fetch && git reset --hard origin/<branch>` between them. Dirty branch with unrelated work: patch out, fresh worktree, apply. Snarled worktree: reset from main, redo minimally.

**Commits.** Commit liberally. Each commit is one coherent step toward its PR's purpose, and fixup commits are fine. When the merge method keeps every commit, as a rebase merge or a merge commit does, squash the fixups before you mark the PR ready. Amend when the fix belongs in a just-made commit. New commit when separable. Before regrouping commits that are already pushed, record `git rev-parse HEAD^{tree}`. Before the force-push, confirm the tree hash is unchanged. A different hash means the regroup changed content, so stop and restore the original branch. Run each history-rewriting git step (rebase, amend, reset, cherry-pick) as its own command and read `git status` before the next.

**Authorship.** The user is the sole author of everything you produce: commits, PR titles and bodies, review comments, code, and docs. Before the first commit, read `git config user.name` and `git config user.email`. When either names a model, an agent, or a harness, set the repository's local identity to the user's, such as their forge noreply address, and ask once when you cannot find it. A forge squash adds a co-author trailer for every other commit author, so make every commit on the branch use the user's identity, and confirm it with `git log --format='%an <%ae>' <base>..HEAD`. Write each message with no co-author trailer for a model or agent, no "generated with" line, no session link, and no model name, even when the harness asks for them. When the user's organization enforces attribution through managed settings, keep it and tell the user. A PR or comment tool can append its own footer after you post, so read back each PR body and comment you post and edit out any attribution it added. When the footer comes back after one edit, stop editing it and tell the user. Keep it out of trunk by setting the squash commit's body yourself when you arm the merge, such as with `gh pr merge --auto --squash --body`. Host settings that switch off the harness's own attribution are in its host note.

**PRs.** Run the **deslop** skill over the diff before commit. Run `no-comments` before review, and let its edits land before you start any reviewer, so every reviewer judges the tree that ships. Write every PR title, PR description, and commit body with `technical-writing`, then apply `simple-as-prose`. Apply every technical-writing layer except Diátaxis. Use one word for each action, keep articles, and avoid `-ing` when a plain verb works.

**Titles.** Use Conventional Commits in the form `type(scope): subject`. Use `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf` as the type. Use the changed area, such as `cstack-mode` or `swarm`, as the scope. Keep the subject short and imperative. Name a real symbol when one carries the change. For example, `fix(cstack-mode): retarget opening-a-pr babysit trigger`. Do not add a trailing period.

**Descriptions.** The PR body is a briefing, not the lab notebook. A reviewer who has the diff should learn why the change exists, what is out of scope, and how you proved the change works. The squash commit body is the PR body. If the body would make the squash commit longer than about 40 lines, cut the body.

Use these sections in order. Drop a section when it has nothing to say.

- `## Why`. Open with the PR's purpose in one sentence. Then state the intent and approach in one or two short paragraphs. Do not list SHAs or rebase genealogy. Do not add a "based on main" preamble.
- `## Scope`. Use bullets to list real symbols and paths. Name both sides of a rename or retarget. State what is in and out only when the boundary matters. Do not write a file-by-file essay.
- `## Tradeoffs`. Name only rejected alternatives that a reviewer would otherwise ask about. Skip this section when there was no real choice.
- `## Blast Radius`. In one to three sentences, name who or what the change touches and why the change is safe or risky. State the continuing cost if main stays red without the fix. End with a door call. Call it one-way when the merge is hard to undo, such as a schema migration, a public API, or deleted data. Call it two-way when a revert is cheap. The reviewer then knows how careful the merge must be.
- `## Verification`. Name each real run path and its outcome. Name any failure that passed on rerun, and link the follow-up you filed for it. A rerun pass does not clear a timing or locking test. For a performance change, report one primary number with its unit in `before → after` form. Link the arena or swarm directory for the remaining evidence. Do not include sample-size methodology, swarm recitals, or metric tables.

**Spec PRs.** When the **align** skill produced a signed spec, the bottom PR's description is that spec, and the 40-line limit gives way to it. Every PR in the stack ends with an `## Evidence` table in place of `## Verification`: one row per acceptance criterion it proves, every kind of proof that criterion's verification row names, and a verdict. Link or inline each proof so a reviewer can judge the PR from the table alone, before or after the merge. A PR that proves no criterion, such as a prefactor, keeps `## Verification`.

```markdown
| AC | Test | Eval | Live check | Review | Verdict |
| --- | --- | --- | --- | --- | --- |
| AC-1 | `test/tags.test.ts` passes, 6 cases | n/a | [terminal capture](link) | interrogate: met | VERIFIED |
```

After these sections, attach videos or screenshots when they prove a claim. Do not paste full SHAs, swarm or arena lane recitals, lever-correction essays, file-by-file checklists, or "CLEAN" verdicts. Put these details in a linked artifact. Do not use `## Summary` or `## Test plan` boilerplate. A commit body does not restate its subject.

**Forge.** Resolve the forge before the first PR operation and keep that choice for create, edit, view, watch, and merge. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, prefer `origin pr ...`. If Origin is absent or cannot resolve the repository, stay on `gh` and record the fallback. Do not require Graphite (`gt`).

**Size and stacks.** Give each PR one purpose a reviewer can state in a sentence. That is what atomic means, not the smallest diff. Cut each PR as a vertical slice, a narrow path through every layer its purpose touches. Split by purpose, never by layer or line count, and stack the pieces. Each new type, field, helper, or endpoint ships in the PR with its first caller, such as the client code that calls a new endpoint. A caller is production code, or an outside consumer of a public seam. A test is not a caller. Merge two PRs when neither is demoable or verifiable alone. A prefactor, a subtraction, or scaffold that runs when it lands is verifiable alone. A stack is a base-branch chain. The root PR targets trunk. Each child branch rebases onto its parent's exact tip and its PR targets the parent branch. When a parent's commits are rewritten, by an amend, a regroup, or a squash merge, record the old parent tip first and move the child with `git rebase --onto <new-parent> <old-parent-tip> <child>`; a plain rebase replays the old parent commits and can conflict on them. After a squash merge the new parent is trunk, so also retarget the child's PR to trunk. A merge of trunk instead makes every shared file conflict. Create a child as a draft per **Readiness**, with `gh pr create --draft --base <parent-branch>` or the Origin equivalent. Retarget an existing child with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Branch from trunk only for independent work. A PR whose text states another open PR's change as done depends on that PR, so stack it on that PR or word the text so it holds in any merge order. Rebase on trunk before substantial stack work.

**Readiness.** Ready for review means approved by agents. Open every PR as a draft. A review and a verification each pass by an agent that did not build the change. The owner may run either gate itself when it did not build the change. It writes its own cases and records truthfully who ran what. It never credits a run to an agent that did not do it. Starting a separate agent is allowed where that is faster. The owner checks the records and marks the PR ready as soon as both gates pass on the finished change:

- **Review.** The review agent reads the finished diff and judges it. When delegating the review, run a fresh-context reviewer on the `review` role per the runtime contract. Give it the review criteria below. Fix its proven findings, and name any mitigated or deferred finding in the PR description.
- **Verification.** The verification agent runs the changed thing end to end on the real surface and proves it works, per `../../principle-prove-it-works/SKILL.md`. It picks the live task from the changed passages. For a docs-only or instruction-only change, it runs a realistic case of the changed workflow. It lists each changed claim the run did not reach as NOT VERIFIED. The builder's own runs are evidence for that agent, not this gate. A non-builder owner may supply this gate with its own cases. Record the actual agent, head SHA, run, and result in **Verification**. A run proves only the head it ran on. When a later edit changes the path it exercised, rerun that path on the new head.

At least one gate agent must come from another model family than the builder when the host or a configured runner offers one. When only one family is available, use fresh agents of that family for delegated gates and name the missing second family in the PR. The non-builder owner may still run either gate itself. When no non-builder agent can run a gate, keep the draft and name the missing gate. CI, a retro, and a person's review or permission are not readiness gates. A failing check is fixed while the PR stays ready, whether the check is required or optional.

An agent that fixes a finding is a builder of that fix wave. A rule or behavior change in a fix wave needs fresh review by an agent that did not make it.

The review covers the finished change and its claims:

- `deslop` and `no-comments` ran on the final diff. Review-bot findings are triaged per `../references/bugbot-triage.md`. A bot that skips drafts gets its first pass after ready, and its proven findings get fixed then.
- Every new or changed test calls a public seam and runs libraries for real. Give the reviewer `../../principle-test-behavior-not-implementation/SKILL.md`. Before accepting a suggested test fix, plant the regression it names and watch the fixed test fail.
- The PR description matches the final diff per **Descriptions**. A live run that proves only part of a claim leaves the rest NOT VERIFIED. Narrow the claim and tell the person. A claim of parity covers everything the run produced, including any false statement in its reply.
- The PR has one purpose, and each new type, field, helper, or endpoint has a caller per **Size and stacks**.
- Each bug fix closes its class at the chokepoint per `../../principle-fix-root-causes/SKILL.md`. Unfixed sibling sites in scope are findings.
- Commit authors, commit messages, and the PR title and body meet **Authorship**. Answer or close any question the change settles. Tell the person when review corrects a fact or an approved plan.

Create the draft with `gh pr create --draft`, or the resolved forge's draft option. As soon as both gates pass, run `gh pr ready <number>` or `origin pr ready <number>`, even with a failing check or no retro record. Report ready separately from mergeable. Forge conflicts, unresolved threads, required approvals, and required checks still govern merging.

Verify each push to an armed PR before it leaves your machine, because auto-merge can survive a push. When a new patch needs renewed review or verification, or a proven finding withdraws an approval, disarm auto-merge and return to draft until both gates pass again. A CI failure alone does not withdraw approval or return the PR to draft. Use `gh pr merge --disable-auto <number>` and `gh pr ready --undo <number>`, or the resolved forge's equivalents. If the forge has no draft conversion, report the missing approval in a PR comment. If drafts are unsupported, put `Awaiting agent approval: <missing gate>` on the first line of the description and remove it when both gates pass. Read the forge's PR state before reporting it.

**Merging.** Marking ready grants no merge authority. With no `Merging:` line, leave the merge to the person. Read the preference from the instructions you loaded, such as the project's `AGENTS.md` or the person's own instructions file. When both set one, the project's line wins:

- `Merging: manual`, also the default with no line. Mark the PR ready and leave the merge to the person.
- `Merging: auto`. Once both readiness gates pass, arm auto-merge with `gh pr merge <number> --auto --<method>` or `origin pr merge <number> --<method> --auto`, subject to the merge checks below.

Arm only when a `Merging: auto` line or a direct request to merge this PR when ready asks for it. A direct request to merge authorizes that merge through Shipping. A request to merge when ready overrides the standing preference for that PR alone, subject to the merge checks below. An armed PR stays yours until it merges or you disarm it, per **Armed PRs** in `playbooks/babysit.md`.

The method is the one the line names, as in `Merging: auto, rebase`. Without one, use the only method the base allows, else squash when allowed, else a merge commit. Read the allowed methods and auto-merge setting with `gh api repos/<owner>/<repo> --jq '{allow_auto_merge, allow_squash_merge, allow_merge_commit, allow_rebase_merge}'`, and the base's rules with `gh api repos/<owner>/<repo>/rules/branches/<base>`. Its `pull_request` rule can narrow the methods, and `required_status_checks` lists the required checks. For classic protection, read `gh api repos/<owner>/<repo>/branches/<base>/protection/required_status_checks`.

Resolve conflicts and unresolved review threads, meet required approvals, and triage review-bot findings before arming. Arm while checks run only when every pending check is required. With no required checks or with an optional check pending or failed, fix and pass those checks before arming, because auto-merge may merge at once. Keep the PR ready throughout. When auto-merge is off, report that the person must merge. Arm only a PR whose base is trunk. A stack child waits for its retarget per `playbooks/shipping.md`. A bot that skips drafts and is not a required check must get its first pass triaged before arming.

The retro never blocks a merge. Where an older installed `Retro` status still waits for a recap, update its reporter per the **Retro status** section in `../../reflect/SKILL.md`. Report that repository limitation without treating it as missing agent approval. Leave merging to the operator or a verdict gate when the running playbook or plan assigns it there. Lessons PRs follow the same merging preference. When merging deploys, apply **Always pause** in the mode skill. A person's instruction on one PR overrides the standing preference for that PR.

**Retro.** After marking ready, invoke `reflect` in PR retro scope and post its recap while the building session still holds the work. It never holds readiness or merging, and may finish after the merge. The builder owns the recap. If the builder is gone, use the PR record and name the missing session evidence. A retro never edits the PR under retro. Any lessons land in a separate PR.

**Babysit.** A PR in a stack that is still being built does not get its own babysit. Post the URL and keep building, then run one babysit pass over the whole stack once it exists. A standalone PR, with no parent or child in the same build, is a finished stack once it opens. The agent that opened it runs `playbooks/babysit.md` in `drive` on that PR until both agent readiness per **Readiness** and forge-clear hold, or merges when armed per **Armed PRs** in `playbooks/babysit.md`, or until only items the agent cannot close remain, and it reports those. A babysit for each new PR in an unfinished stack stalls the build and spends checks on commits that later waves restart. Push back when feedback drifts from intent.

A subagent that opens a PR runs `deslop` and `no-comments`, plus `interrogate` when the design is contested, and posts the URL. A subagent that opened a standalone PR then drives it to agent-approved readiness and forge-clear per **Babysit** before it returns, unless its brief says to return at the URL. A subagent that opened one PR of a larger stack returns to the parent without babysitting, unless it is an Autopilot-full or Autopilot-stack owner. That owner's brief assigns the babysit loop and is the ask `playbooks/babysit.md` waits for. The owner starts the loop after its code-ready report and reports loop-green or STACK-READY as its playbook says. The rules here and in `playbooks/babysit.md` that hold babysitting until a whole stack is built do not apply to that owner.

# Set up the plugin

Read [the runtime contract](../cstack-mode/references/runtime.md) and the host note for this harness. The plugin runs on the host's model unless the person sets model roles, so setup covers only what a person and a project must change once.

Work through each item. Fix it when the fix is a file change in the project or in the person's own host settings. Show each change with the value it replaces, and use the **Ask** capability to get the person's yes before you write outside the project. When an item needs a setting only the person can reach, give them the exact setting and where it lives. Leave project edits uncommitted for the person to review.

1. **Install.** Confirm the plugin loaded: this skill and the `<plugin>-mode` skill appear in the host's skill list, and a read of `<plugin-root>/skills/<plugin>-mode/SKILL.md` succeeds. Where the host note says the plugin's hooks need the person's trust or say how a missing hook shows, check that and report it. Where the host note names an install command, run it and report what it printed. A `kept` line names an entry of the person's own that blocks a link, which they resolve.
2. **Attribution.** Read the host note's attribution paragraph. Where the host has a setting, an unset key counts as on. Write the form the host note gives that works on every version it names, in the person's own settings file, because attribution is a personal choice across projects. When the session runs in an environment that resets on start, write it in the project's settings file instead, and tell the person it survives a reset only once they commit it. Where the host has no setting, or attribution that no setting removes, report that the **Authorship** rule in [opening-a-pr](../cstack-mode/playbooks/opening-a-pr.md) is the remaining control.
3. **Commit identity.** Apply the **Authorship** rule's identity check to the project. Ask once for the person's name and email when the project, their global git config, and their forge account do not supply both. An identity that names a model, an agent, or a harness supplies nothing. When the session runs in an environment that resets on start, also tell the person to add the same two settings, with `--global`, to the environment's setup script, because a new environment starts with the harness identity again.
4. **Mode.** Read the instructions file each host note names. Put the mode line in `AGENTS.md` at the project root, and create the file with only that line when it is missing. When this host's instructions file is another file, make it import `AGENTS.md` the way its host note shows, at the end of the file. When a host note says its host follows no imports, put the mode line itself in the file that host reads, above any import. When no line already invokes `<plugin>-mode` first, add this line near the top, with `<plugin>` resolved to the plugin's name:

   ```markdown
   Invoke the `<plugin>-mode` skill as your first action in every session in this repository, before any other tool call. Work under it for the rest of the session unless the user turns it off.
   ```

   The hooks keep the mode on only on a machine where the person typed its command or set the variable below, so every other session relies on this line.

   Then ask once whether the person wants the mode on in every project they work in, including repositories without this line. The switch is an environment variable whose name is `<plugin>-mode` in capitals, with `_` for `-`. When it is `on`, the hooks turn the mode on at session start in every project the person has not turned off. On a yes, add `export <variable>=on` to the person's shell profile, and tell them the harness reads it only when it starts from a shell that loaded that profile. When the session runs in an environment that resets on start, tell them to set the variable in the environment's settings instead. When the host note says the host runs no plugin hooks, give the person the note's personal rule to paste instead of the variable.
5. **Merging.** Read the base branch's required checks, its allowed merge methods, and whether the repository allows auto-merge, with the commands in **Merging** in [opening-a-pr](../cstack-mode/playbooks/opening-a-pr.md). Ask the person once whether agents should arm auto-merge when they mark a PR ready, with which method when the base allows more than one, and whether it holds for this project or for every project the person works in. When the answer differs from that rule's default, write one `Merging:` line, such as `Merging: manual` or `Merging: auto, rebase`. For this project, add it to `AGENTS.md`, where it applies to everyone who works here. For every project, add it to the user instructions file named in the host note, after their yes. When the host note says the host has no such file, follow what it says instead. When the session runs in an environment that resets on start, tell them a user-level file does not survive the reset. Then report what the repository forces whatever the preference says:
   - No required status checks: agents arm only after every check passes. Name the forge setting that makes a check required.
   - Auto-merge off: agents mark the PR ready and leave the merge to the person. Name the forge setting that allows auto-merge.
6. **Models.** Read **Model roles** in the runtime contract. Read any `Models:` block already in the user instructions file named in the host note and in the project's instructions files, and report each project line that names a command as ignored. List the agent CLIs on the PATH, such as `codex exec`, `claude -p`, and `cursor-agent -p`. Then ask the person once which runner and options each of `build`, `review`, `advisor`, `explore` (read-only search lanes, a fit for a fast model), and `image` should use, and whether each `native` line holds for this project or for every project. A role can list several runners separated by `;`, one per panel seat. Every role except `image` defaults to the host's model. `image` uses the host's **Generate an image** capability when the host note maps one. When the note maps none, report image generation as unavailable until an `image` line names a CLI runner. Check each line before you write it, and tell the person each check runs their CLI on their account. Run each CLI runner from a temporary directory with stdin closed and a time limit, pass a one-line read-only brief by file, and add the model, effort, and speed flags from its `--help`. A missing CLI, a timeout, a nonzero exit, a sign-in prompt, a rejected model or flag, or no final message is a failure. Leave a failed line unwritten, even when the person already said yes, and report the failure with the fix it needs. For a `native` line, name each option the host note says this host cannot apply. When any role differs from its default, write the lines after their yes. Put `native` lines for this project in a `Models:` block in `AGENTS.md`, where they apply to everyone who works here. Put every other line in a `Models:` block in the user instructions file, because the runtime contract takes a command runner only from that file. When the host note says the host has no such file, follow what it says instead. When the session runs in an environment that resets on start, tell them a user-level file does not survive the reset, and offer the lines that append the block to that file from the environment's setup script, as item 3 does for git identity.
7. **Dependencies.** Check the tools some workflows need and name each one that is missing: Bun with the plugin's locked helper dependencies for the bookkeeping helpers, `gh` for the PR watcher, and Graphite for the Orchestrate stack frontier. Leave installs to the person.
8. **Verification.** When the project has no scripted way to prove its UI, CLI, or service behavior, offer the **create-verification-skill** skill once.

Report a table with one row per item and these columns: state before, change you made, action left for the person, and state after. Setup is done when every row is fixed, already set, or names an action for the person.

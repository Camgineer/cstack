# Intent host note

Apply [the runtime contract](../runtime.md) first. This note maps its capabilities to Intent, a workspace app whose daemon, `intentd`, runs Claude Code, Codex, and other agent CLIs as providers. You are in Intent when your tools include `workspace_api` and your system prompt lists `<available_skills>`. Claude Code's own tools can still appear there, so follow this note rather than the Claude Code note.

Checked at: intentd 0.10.33

Every claim below was checked at that release, which `intentd --version` prints in the same form. Each claim that says "read from source" links `intentd`'s source at the `v0.10.33` tag. Each claim that says "observed" was seen on a 0.10.33 daemon. A newer daemon can differ, so recheck a "cannot" or "has no" claim before you design around it.

The plugin reaches an Intent agent by two routes. Intent's own skill catalog and specialists are the first, and `hooks/intent-install.sh` fills them. The provider is the second. Intent no longer isolates its providers. Release 0.10.25 reverted the daemon-owned provider configuration ([intentd PR 2331](https://github.com/intent-hq/intentd/pull/2331)), so a provider loads its own plugins and hooks inside Intent. A person who also installed the plugin in Claude Code or Codex gets that copy and its session-start hook in every Intent agent on that provider. This was observed on a Claude Code agent and on a Codex agent.

| Capability | Native route |
| --- | --- |
| **Delegate** | `ws.agent.delegate` through the `workspace_api` tool ([bindings, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/bindings/agent.rs#L729-L745)). Put the brief in `agentInstructions`; no task note is needed. Pass `specialist: "cstack-agent"` or `specialist: "comment-sicko"` for a bundled persona. Put a routed workflow's own prompt in the brief, because `behaviorPrompt` does not arrive. Intent removes Claude Code's native `Task` subagent tool ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_session.rs#L1838-L1866)). See **Delegation limits** below. Read results with `ws.agent.readConversation`. |
| **Ask** | `ws.app.question.ask`, when the session's structured-questions feature is on. A delegated agent cannot ask structured questions: Intent rejects every `app.question.*` call from a delegate ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/dispatch.rs#L962-L967)). Otherwise ask in the reply and continue on reversible work. |
| **Plan** | Intent tasks: `ws.note.listTasks` to read them and `ws.task.update` to change status. |
| **Invoke a skill** | Intent lists each installed skill in the system prompt with its `location`. Read that `SKILL.md`. A provider that has its own copy of the plugin offers each skill a second time, through the provider's skill tool. Use the copy in Intent's list, because the provider's copy can be an older release. The installer links no `principle-*` skill, so none is listed. Read them at `<plugin-root>/skills/<name>/SKILL.md`. |
| **History** | `ws.agent.readConversation` for other agents in the workspace. Otherwise use a transcript or digest the user supplies. |
| **Continue later** | `ws.hook.schedule`, which wakes the agent when its check passes, and `ws.pr.monitor` for pull-request events, while the background-hooks and PR-monitor features are on. |
| **Generate an image** | None. An `image` line naming a CLI runner, such as `codex exec`, provides it. |

Delegation limits. Depth counts from the agent the person started, which is depth 0, and `ws.agent.status` on your own id shows yours as `metadata.delegationDepth`. An agent at depth 2 cannot delegate ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/bindings/agent.rs#L1484-L1487), and observed). Its call fails with this text:

```text
Cannot delegate task: maximum delegation depth (2) reached. You are at depth 2. Please complete this task directly instead of delegating further.
```

`ws.agent.delegate` accepts `behaviorPrompt`, and no code in the delegate service reads it (read from source: the [binding](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/mcp_server/bindings/agent.rs#L738) parses the field). One Claude Code child and one Codex child, each delegated with a specialist and a behavior prompt, saw the specialist's own prompt and not the behavior prompt (observed, one run each, self-reported).

Skill directories. `<project-skills>` is `.agents/skills` in the project, which Intent and Codex outside Intent both read. `<user-skills>` is `~/.intent/skills`. Intent scans eight roots ([skill discovery, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/skills.rs#L191-L253)). When two roots hold a skill of the same name, Intent lists the one from the higher root in this order:

1. `.intent/skills` in the project
2. `.augment/skills` in the project
3. `.claude/skills` in the project
4. `.agents/skills` in the project
5. `~/.intent/skills`
6. `~/.augment/skills`
7. `~/.claude/skills`, or `skills` under `CLAUDE_CONFIG_DIR` when that is set
8. `~/.agents/skills`

Intent does not scan `.codex/skills`, in the project or in the home directory. Intent names a skill from its frontmatter `name` and lists any `SKILL.md` it finds in a root, a `principle-*` skill included.

Instructions file. Intent adds one project file to every agent's system prompt: the first of `CLAUDE.md`, `AGENTS.md`, `.intent/guidelines.md`, and `.augment/guidelines.md` that exists, or else every `.intent/rules/*.md` and `.augment/rules/*.md` ([rules, read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/rules.rs#L83-L200)). It does not follow `@` imports. The provider can also load its own instructions file, as Claude Code does with `CLAUDE.md` and its imports. In a project with a `CLAUDE.md`, put the mode line in `CLAUDE.md` itself, above any import of `AGENTS.md`.

User instructions file. None. Intent keeps a person's rules in its settings store, under Settings, Agent Behavior ([settings](https://intentapp.dev/docs#settings-configuration)), so give the person the rule text to paste there.

Model roles. A `native` role passes `provider`, `model`, and `reasoningEffort` to `ws.agent.delegate`. Pass `provider` with every `model`. A call that passes a model without its provider drops the specialist's provider, and Intent uses its default provider ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/agent_ops.rs#L10666-L10682), and observed). The plugin's personas set no provider or model, so they run on the person's defaults. Set a persona's model with a `Models:` block. A delegate with no `specialist` gets no specialist prompt and runs on Intent's default provider, model, and effort settings (observed in `ws.agent.status`; the missing prompt is [read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/lib.rs#L2359-L2400)).

Specialist files. A specialist is a Markdown file whose body is the prompt. Intent reads these frontmatter keys ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L402-L446), with the other keys defined in the same file): `name`, `description`, `codingAgent`, `model`, `reasoningEffort`, `roleReminder`, `agentType`, `role`, `icon`, `hidden`, `modelOptions`, `teamAgents`, and `aliases`. No key names skills or permissions.

- Tiers. Intent folds its built-ins, then `~/.intent/specialists`, then `.intent/specialists` in the workspace's own root, and the last file with an id wins ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1286-L1296)). A project file is listed by `ws.agent.listSpecialists` (observed). Intent reads it from the workspace's root, and a copy in an agent's sandbox was not listed (observed).
- A same-id file replaces a built-in's whole prompt, name, and description ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L901-L921), and observed: a `verifier.md` that held only `reasoningEffort` left that specialist with an empty prompt). The keys `codingAgent`, `model`, `reasoningEffort`, `agentType`, `role`, `icon`, and `modelOptions` inherit from the lower tier when the file omits them.
- Tool limits. `role: orchestrator` removes the file-write tools and leaves the shell. `agentType` removes tools only for Intent's background types: `commit-message`, `pr-description`, `code-review`, and `code-walkthrough` lose the write, git, execution, and delegation tools, and `task-loop`, `ralph-loop`, and `chat` lose the subagent tools ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-acp/src/tool_restrictions.rs#L121-L185)). Neither makes a read-only sandbox.
- `modelOptions` is an advisory menu, written as a JSON array on one line. Intent shows it in every agent's `ws.agent.delegate` tool description and checks no call against it (read from source), so apply an entry by passing its provider, model, and effort. When a call passes no effort, the first entry that matches the resolved provider and model supplies the effort, ahead of the file's own `reasoningEffort` ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/specialists.rs#L1143-L1161), and observed).
- Intent's specialist editor writes through the installed link into the plugin's own file.

Plugin root. Take it from a skill's resource directory, which the system prompt lists as `resource_directory` and `skill.list` returns as `resourceDirectory`. For a linked skill that is the skill's real directory, and the plugin root is two levels above it. The skill's `location` is the installed link under `~/.intent/skills`, and the path above that link does not hold the plugin.

Install. The person runs `npx -y github:<owner>/<repo>` with the plugin's repository, and runs it again to update. It runs `hooks/intent-install.sh`, which copies the plugin to `${XDG_DATA_HOME:-~/.local/share}/<plugin>`, replacing the last copy, because npx's cache can vanish. From a git checkout, such as a clone of the plugin being worked on, the script links to the checkout instead, and a rerun after `git pull` updates it. Either way, it links every skill except the principles into `~/.intent/skills` and both personas into `~/.intent/specialists`. It replaces only its own links and broken ones, and reports every other entry in the way as `kept`. Run from another host's plugin cache, it copies too, so its links never point into a cache that host replaces.

Persistent mode. Two things can turn the mode on in Intent. The first is the provider's own copy of the plugin: its session-start hook runs inside Intent, so `hooks/mode.sh` and `CSTACK_MODE` take effect for an agent on that provider. The hook's text was observed in a Claude Code agent and in a Codex agent, and `CSTACK_MODE` was observed in a Claude Code agent's shell. The second is an instruction. The project's instructions file covers one repository. For every project, the install's first run adds this personal rule through `intentd call rules.update` with `ruleType` `workspace`:

```markdown
Before any other step, read the `<plugin>-mode` skill's SKILL.md from your skills list and follow it for the rest of the session.
```

Intent stores the rule as the first paragraph of the person's own rule text, with nothing that marks it as the plugin's. It reaches ordinary workspace agents and their delegates, and not the Assistant workspace ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/rules.rs#L471-L500)). When the installer can't reach `intentd`, or the person's rule is switched off, it prints the rule for the person to paste under Settings, Agent Behavior. The person turns the rule off by removing that paragraph.

Sandboxes and attribution. Each delegate works in its own sandbox: a checkout under the workspace's `sandboxes/<agent id>/` directory, on a branch named `sb/<agent id>` (observed). Two paths commit a delegate's work.

- Intent's `git.autoCommit` setting is on by default. When a task-linked agent goes idle, Intent commits its changes with a generated message and `Agent-Id:` and `Linked-Note-Id:` trailers, outside the **Authorship** rule in `playbooks/opening-a-pr.md`. Pass `skipAutoCommit: true` to `ws.agent.delegate`, which skips this commit ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/auto_commit.rs#L262-L277)), and give the person the setting to turn off: auto-commit in Intent's Git settings, or `intentd settings git.autoCommit false`.
- When Intent merges a sandbox back, it first commits any uncommitted change there with the subject `Auto-commit dirty state for <agent id>` ([read from source](https://github.com/intent-hq/intentd/blob/v0.10.33/crates/intent-services/src/sandbox_ops.rs#L404-L445)). In one observed run that commit landed on the workspace's own branch when the delegate's turn ended, with the machine's git identity and no trailers, and `skipAutoCommit: true` did not prevent it. The sandbox, its branch, and its worktree were then gone.

Observed, cause not established: an agent's own sandbox was emptied while it waited on agents it had delegated to. This was seen in more than one run. A guess at the cause is that Intent reclaims a sandbox when the agent's turn ends or its delegation group settles.

Headless runs. `intentd` runs without the desktop app. The `intentd` on `PATH` is a small launcher that downloads the daemon on the first `serve` under a new `HOME`. On macOS it keeps the daemon at `~/Library/Application Support/intentd/sitter/versions/<version>/intentd`. Run that versioned binary directly when the launcher's download fails, or to pin the release under test. Where the download fails behind a proxy, fetch the asset that the [stable channel manifest](https://github.com/intent-hq/intentd-releases/releases/download/channel-stable/stable.json) lists, check it against the manifest's sha256, and run the `intentd` inside it. Start `intentd serve` with a disposable `HOME`, and keep the socket path short enough for the Unix socket limit: the socket sits under `HOME` on macOS and under `XDG_DATA_HOME` on Linux. `intentd status` shows the socket path and whether the daemon is up. Create a workspace with `intentd call workspace.create --params '{"title":"probe"}'`. Then `intentd call skill.list` and `intentd call specialist.list`, each given that workspace's id as `workspaceId`, show what Intent's agents see, with no provider signed in. `specialist.list` returns a project's specialist files only with `includeProject: true`. On a failed call, `intentd call` prints an error line after the JSON, so parse stdout alone.
